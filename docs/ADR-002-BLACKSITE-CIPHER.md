# ADR-002 — BLACKSITE as a confidential deduction game
Status: accepted as **rules-only research**; NOT committed to a contract or public UI
Date: 2026-11-21
Parent: [ADR-001](ADR-001-CORE-GAME.md), [Production Charter](PRODUCTION_CHARTER.md)

## Decision and problem

The initial "encrypted random traps" infiltration idea risks feeling like blind guessing. We instead evaluate **BLACKSITE / Vault Cipher**, a separate single-player FHE use case: a secret onchain security code, public constrained hints to player-submitted guesses, and a skill-based deduction/escape loop.

A future infiltration mission can surround this with reconnaissance, combat preparation and narrative tension, but the puzzle engine must be fun, testable and fair before any graphics or stealth animations.

This is **not** Arena. It has a different privacy objective:
- Arena: protect human players' selected tactics, calculate private-versus-private matchup and publish only aggregate results.
- BLACKSITE: hold a generated vault secret privately, evaluate guesses without exposing it outright, return **limited deliberate feedback**. As the player deduces the code the secret may become inferable; this is the puzzle goal, not a permanent confidentiality guarantee.

## Current rules-only prototype

Implemented **only** in `src/research/blacksite-cipher.mjs`:
- Four positions, four possible glyphs per position (0–3), duplicates allowed; `4^4 = 256` valid codes.
- Each guess returns `exact`: number of symbols in correct positions; `misplaced`: number of correct symbols in different positions, accounting for repeats. This is classic codebreaking feedback, not an invented gameplay novelty.
- Standard budget: 5 guesses; 4 for expert and 6 for training. Duplicate guesses rejected without spending an attempt. First exact-4 clue wins; otherwise the last permitted miss locks the vault.
- Public feedback events contain the submitted guess, clue totals and remaining attempts; they never expose the stored secret field.
- A deduction helper filters all possible codes by only the public history.
- This is a **cleartext reference simulation** with an injected test secret. It is NOT onchain randomness or encryption, and must not be imported as a live secret authority.

### Mathematical feasibility, not human playtest evidence

`tests/blacksite-cipher.test.mjs` exhaustively checks all 65,536 secret/guess pairs for valid and symmetric repeat-aware feedback, checks disclosure redaction and duplicate-state abuse, and simulates a minimax solver against all 256 secrets.

An offline minimax strategy previously tested in the design exploration solved every secret within four queries (worst case four, average approximately 3.59). The committed tests must pass in CI before this is considered reproduced evidence. **This does not establish that an unaided human can solve it in four or five attempts.** Five or six guesses may still be too easy or too hard for human players; only blind playtesting can decide.

## Intended production UX loop (not yet built)

1. Player accepts a BLACKSITE infiltration mission.
2. A public mission descriptor identifies the target vault and puzzle rules. The encrypted code is generated by a contract, never chosen from JavaScript `Math.random()`.
3. Player studies accumulated clue history, chooses a tactical four-symbol guess and confirms it.
4. Contract evaluates the guess against encrypted code. A signed public-decryption proof authorizes the intentionally limited `exact, misplaced` clue.
5. The player sees authenticated aggregate hints and decides the next guess.
6. Breach success or attempt exhaustion settles the mission. A finished mission can be replayed as a *new* secret; it never resets the same security code to enable unlimited oracle queries.

A basic BLACKSITE mission must stand alone as an understandable deduction puzzle. Combat, exploration, characters, equipment and rewards can layer on ONLY after puzzle playtests, onchain feasibility and time budget support them.

## Proposed onchain state machine (candidate, no Solidity written)

`MISSING → GENERATED → GUESS_PENDING → HINT_READY → HINT_VERIFIED → (GENERATED for next guess | BREACHED | LOCKED)`.

State data candidate:
- Mission ID, owner, expiry/closed state, max attempts and number of authenticated tries.
- Encrypted 4-glyph secret, generated using Zama's authenticated onchain encrypted PRNG. Using one encrypted `euint8` and 2-bit extraction is a research optimization, not a validated implementation.
- Current pending guess hash or exact public guess; a handle to **one** encrypted packed feedback number; one-time proof/nonce binding to prevent stale proof reuse.
- Public immutable clue history and final mission status; no raw secret getter or event.

Authorization model:
- Only mission owner can submit its permitted guesses. A third party may optionally finalize the exact pending hint using a valid Zama signed public decryption, but cannot provide a new guess or claim rewards.
- A guessed code may be public. If private guesses are required later, that changes both cost and threat model, so don't imply privacy for guesses now.
- Reject concurrent guesses while awaiting KMS proof; prevent arbitrary brute-force sessions from restarting against one secret.
- Intentional partial decryption reveals only a bounded clue, not the 4 glyphs. `exact*5 + misplaced` can encode both counts in one `euint8` ciphertext because misplaced is in [0,4].
- The verified hint must match the current encrypted handle and the mission ID / attempt number; onchain proof binding and one-use advancement are mandatory.
- A win is authenticated only after the valid hint is finalized. Do not award valuables, rank or competition points from client-only codebreaking.

## FHE feasibility work needed BEFORE Solidity

- Confirm current Zama `FHE.randEuint8()` / bounded randomness behavior, chain costs and ciphertext handling; random creation requires a state-changing transaction.
- Design duplicate-aware Mastermind hint arithmetic from FHE operations. Exact is four encrypted equalities + sums. Misplaced requires encrypted symbol-frequency intersection and min/subtract; count op inventory and **sequential** HCU depth against live network, not just devnet documentation.
- Compare two circuits: (A) full exact + misplaced clues versus (B) reduced clue output with better computational cost. Re-run exhaustive solver feasibility with the reduced-feedback rule if applicable.
- Validate proofs and latency with real Sepolia in a one-shot, approved transaction before building a five-guess onchain mission.
- Budget user transactions realistically: one FHE guess and one public-proof finalization may be asynchronous and can require more than one signature; repeated onchain guesses may be too slow. If so, redesign the flow instead of pretending instant puzzle turns.
- Confirm no untrusted relayer/server can create a fake mission secret, forge an aggregate clue, reuse another mission's proof or expose raw code via logs.
- Evaluate if making hints public lets bystanders solve a live puzzle before the player; scope mission ownership and any future rewards accordingly.

## Falsification criteria

Do NOT promote BLACKSITE to production if:
- New users cannot understand exact versus misplaced feedback without a lengthy explanation.
- Humans solve or fail too predictably and don't want to retry.
- The FHE hint circuit exceeds measured limits or the 5-turn onchain flow is tedious.
- Encrypted randomness or bounded query authorization cannot be proved.
- Public hints produce an unacceptable exploit for intended rewards.
- The quest's difficulty comes from waiting on transactions, not gameplay.
- It delays the first genuine Arena encrypted match without materially strengthening the product.

## Release boundary

Arena live match remains the **P0** proof gate. BLACKSITE is isolated, rules-only code and tests. No new public route, Phaser screen, Solidity deployment, token economy, signature, gas spending or claim of functioning encrypted vault was made by this ADR.
